# Experiment folders: one place for every user setting

Design note, Phase 8a (maintainer, 2026-11-01; decision 91 in [`decisions.md`](decisions.md)).
**Implemented 2026-11-01** (`clm_ml.experiment`; what changed with it: decision 91).
Replaces how runs are configured today (decisions 89 and 90 revised). No science change: a
CHATS7 experiment folder must give results bit for bit identical to today's CHATS7 run.

## 1. The problem

A run needs four kinds of settings, which today live in four kinds of places:

| Setting | Where it lives today |
|---|---|
| run.yaml: dates, forcing, output | the experiment folder |
| model.yaml: schemes, numerics | the folder, or nowhere (Python defaults) |
| params: plant parameters | inside the installed package, by name (`chats`, `clm6`), or a user file |
| towers: sites, soil, patches | inside the package (`towers.yaml`), or a user file named in run.yaml |
| grid: surface data, region | a section of run.yaml |

To see every option you can set, you have to read Python. Some settings also appear twice:
the forcing data interval is in run.yaml (`time.step_seconds`) and in towers.yaml
(`forcing_step_minutes`), and the model step is in run.yaml and in model.yaml
(`numerics.step_seconds`).

## 2. The design in one paragraph

**An experiment is a folder holding four files with fixed names: `run.yaml`, `domain.yaml`,
`model.yaml` and `params.yaml`.** The folder is the only thing a run reads besides the data
files it names, and nothing is read from inside the package at run time. Every file is
**complete**: it lists every setting that applies to it, each with a comment saying what it
means, its units, its choices, its default (or that it is required) and the Fortran name it
replaces. A new experiment is generated from a preset (`clm-ml new`), never assembled by
hand. The model refuses an incomplete file and says how to fix it (`clm-ml upgrade`). Each
run writes a copy of the four files, as the model read them, into its output directory.

```
my_experiment/
  run.yaml       WHEN and WITH WHAT: dates, calendar, forcing and land-data files, initial
                 conditions, output streams, chunks, restarts, devices
  domain.yaml    WHERE: towers (location, forcing height, soil, patches) or a grid (surface
                 dataset, land mask, region)
  model.yaml     HOW: physics schemes and numerics (static: a change recompiles)
  params.yaml    WHICH PLANTS: every parameter of every PFT 1-16 (differentiable)
```

```bash
clm-ml new my_site --from chats7       # write a complete experiment folder from a preset
clm-ml check my_site/                  # validate the four files and print a summary
clm-ml run my_site/                    # run; output and a copy of the four files in output/
clm-ml run my_site/ --set run.time.days=3 --set model.physics.stomatal_conductance=medlyn
clm-ml upgrade my_site/                # rewrite the files with every current key (after an update)
```

## 3. The rules

1. **One folder, four fixed file names.** `clm-ml run DIR` reads `DIR/run.yaml`,
   `DIR/domain.yaml`, `DIR/model.yaml` and `DIR/params.yaml`. No file names other files
   except data (forcing, CLM history, surface data, restart), whose paths are relative to
   the folder.
2. **Each setting lives in exactly one file.** The duplicates in §1 are removed (§5).
3. **Complete and strict.** Every key that applies is present. A missing key, an unknown key
   or a key from another file is an error naming the file, the key and the fix. Required
   keys have no default: a generated file shows them as `REQUIRED` and the model refuses
   the file until they are filled in.
4. **Only the sections that apply.** A tower experiment's files don't show the grid
   settings, and a grid experiment's files don't show the tower ones (`domain.yaml`
   `type: towers | grid` decides). This keeps each file to what the user can actually set.
5. **Presets are starting points only.** The built-in CHATS7 tower, the parameter sets
   (`clm5_defaults`, `chats`, `clm6`) and the 1° grid experiment are copied into a folder by
   `clm-ml new` and `clm-ml convert`. A run never refers to them by name.
6. **Every option's meaning is written once, in the code.** Each run, domain and model option
   is a typed dataclass field carrying its explanation, units, Fortran name and whether it is
   required (as `clm_ml.config` does since decision 90). Params keep their table of
   definitions (`clm_ml.params.PARAM_SPECS`). The generated files, the error messages and
   the reference page of Phase 8b all come from these definitions, so they cannot disagree.

## 4. What a generated file looks like

The same layout in all four files: the file's purpose at the top, then each section with a
one-line description, then each key with its comment block.

```yaml
# run.yaml: when the experiment runs, with which forcing and land data, and what it writes.
# Generated by clm-ml 1.0.0 (`clm-ml new my_site --from chats7`). Every setting is listed;
# keys marked REQUIRED must be filled in. Paths are relative to this folder.

time:
  # The simulated period and calendar.

  # First model time step, ISO date-time.
  # REQUIRED.
  start: 2007-05-01T00:00

  # Length of the run. Give exactly one of end, days, steps; leave the others null.
  # default: null.
  days: 1
  ...
```

For params.yaml the comment block is given once per parameter in a `units`/description
header, not repeated for each of the 16 PFTs, and the header names the preset the table was
copied from (for example "copied from chats: clm5_defaults with the CHATS walnut values").

## 5. What goes in which file

| File, section | Contents | Comes from today |
|---|---|---|
| run `time` | start, end/days/steps, calendar | run.yaml `time` (without `step_seconds`) |
| run `forcing` | meteorology files, their data interval (`interval_seconds`) and interpolation (tower) or gridded streams and CO2 (grid); CLM history file; vegetation and soil-water sources | run.yaml `forcing`; run.yaml `time.step_seconds` and towers.yaml `forcing_step_minutes` (the data interval) |
| run `initial_conditions` | from the CLM history or a restart file | run.yaml |
| run `output` | directory, streams, legacy `.out` | run.yaml |
| run `execution` | chunk length, restarts, devices, padding counts | run.yaml |
| domain `type` | towers or grid | run.yaml `domain.type` |
| domain `towers` | per tower: latitude, longitude, forcing height, soil, patches (PFT, weight, height, root biomass, profiles, layer counts) | towers.yaml (built-in or user); run.yaml `domain.towers` |
| domain `grid` | surface dataset, land mask, region, root biomass, forcing height | run.yaml `domain.grid` |
| domain | minimum patch weight | run.yaml `domain.min_patch_weight` |
| model | physics, numerics (including the model step), canopy layers, soil columns | model.yaml (unchanged) |
| params | `units` and `pft` table | params file (unchanged format) |

The model time step goes in model.yaml only (`numerics.step_seconds`, default 1800 s: a
numerics choice that changes the compiled program; no longer "null = the data interval").
The tower meteorology's data interval is a run.yaml setting
(`forcing.meteorology.interval_seconds`, maintainer 2026-11-01); the model step must divide
it. Grid streams keep their own intervals (CDEPS rules).

## 6. Strictness and `clm-ml upgrade`

When a later version adds, renames or removes a setting, old folders no longer match.
Loading one fails with a message such as:

```
my_site/model.yaml: missing key(s) numerics.new_option (added in clm-ml 1.1).
Run `clm-ml upgrade my_site/` to add them at their defaults.
```

`clm-ml upgrade DIR` rewrites the four files in the current layout: it keeps every value the
user set, adds new keys at their defaults, applies renames from a table in the code (as the
loader's table of old forcing keys does today), refuses to drop a removed key that has a
non-default value without saying so, refreshes the comments, and keeps a copy of the old
files (`DIR/.previous/`). It also converts a folder in today's layout (run.yaml naming a
params preset, a towers file and a model.yaml) into the four files. No version number is
stored in the files: upgrade compares the keys with the code.

## 7. Runs record their configuration

Every run writes `OUTPUT/config/{run,domain,model,params}.yaml`: the four files as the model
read them, with `--set` changes applied and the version recorded. That copy is itself a
valid experiment folder: `clm-ml run OUTPUT/config/` repeats the run. Restart files already
check that the forcing streams match; they will also refer to this copy.

## 8. Python

```python
import clm_ml

exp = clm_ml.load_experiment("my_site/", overrides=["model.physics.stomatal_conductance=medlyn"])
exp.run, exp.domain, exp.model, exp.params        # the four typed, immutable objects
results = exp.execute()                           # as `clm-ml run`
model = clm_ml.Model.from_experiment(exp)         # chunks and gradients (calibration)
params = exp.params.set("broadleaf_deciduous_temperate_tree", vcmax25=100.0)
```

Calibration and ensembles change parameters in Python (`Params.set`, or arrays passed to
`Model.run_chunk`); they don't need shared params files. `clm_ml.new_experiment(dir,
preset)` and `clm_ml.upgrade_experiment(dir)` do what the commands do.

## 9. Repository layout

```
configs/                       the presets written out as complete experiment folders
  README.md
  chats7_1day/{run,domain,model,params}.yaml
  chats7_may2007_fortran/...   (the Fortran comparison)
  grid_1deg_2000/...
src/clm_ml/presets/            the sources `clm-ml new` copies from (package data)
  towers/chats7.yaml           the CHATS7 tower
  params/{clm5_defaults,chats,clm6}.yaml
  experiments/{chats7_1day,chats7_may2007_fortran,grid_1deg_2000}.yaml   (run settings)
```

`configs/` is generated from the presets (`clm-ml new`), and a test checks that every
folder in it is complete and current. `src/clm_ml/data/` keeps only what the physics reads
(`psihat.nc`). `configs/model.yaml` (decision 90) goes away: every folder has its own
complete model.yaml, and `clm-ml new` writes one.

## 10. How this matches jax-gcm

- Configuration is typed, immutable dataclasses passed explicitly to pure functions; the
  YAML files are the user's view of them (unchanged).
- Static choices (model.yaml, a change recompiles) and differentiable numbers (params.yaml,
  gradients come back per PFT) are separate files, so the distinction is visible.
- Validated configurations are named files with comments explaining each setting
  (jax-gcm's "configuration through files, one run command").
- One run command with overrides, and the resolved configuration saved with the output, as
  Hydra does for jax-gcm. We keep plain YAML and our own validation (decision 10).

## 11. Commands, before and after

| Today | After |
|---|---|
| `clm-ml run run.yaml` | `clm-ml run DIR` |
| `clm-ml check run.yaml` | `clm-ml check DIR` |
| `clm-ml convert NAMELIST -o DIR` (run.yaml + model.yaml) | the same, writing all four files |
| `clm-ml params FILE.nc -o p.yaml` | the same (a CLM parameter file into a complete params.yaml) |
| `clm-ml model-yaml` | removed (`new` and `upgrade` write complete files) |
| none | `clm-ml new DIR --from PRESET`, `clm-ml upgrade DIR` |
| `--set time.days=3` | `--set run.time.days=3` (the file named first) |

## 12. Implementation and testing

In order, each step a commit that passes lint, the fast tests, bit for bit and the noise
twin:

1. Option definitions with explanations (field metadata) for every run and domain setting;
   one renderer for complete, commented files (generalizing `clm_ml.config.model_yaml_text`).
2. `domain.yaml` (towers or grid) and the move of the settings in §5.
3. The experiment loader (`load_experiment`, strict) and `clm-ml run|check DIR`; the
   regression tests run from a CHATS7 experiment folder and must stay bit for bit.
4. Presets, `clm-ml new`, `clm-ml convert` writing four files, `configs/` regenerated, the
   test that keeps `configs/` current.
5. `clm-ml upgrade` (including today's layout), the configuration copy in the output.
6. Documentation and examples (README, CONTRIBUTING, CLAUDE.md, `model_overview.md`), the
   weekly CI on `configs/chats7_may2007_fortran/`.

Tests: each file type refuses a missing, unknown or misplaced key with a message naming the
fix; `new` then `run` reproduces the CHATS7 reference bit for bit; `upgrade` keeps every
user value and turns today's layout into one that runs identically; the output's config copy
reruns identically.

## 13. Answers (maintainer, 2026-11-01)

1. **File names:** `run`, `domain`, `model`, `params` (kept).
2. **The data interval:** a run.yaml setting (`forcing.meteorology.interval_seconds`), not
   read from the files.
3. **Test-only settings** (such as `domain.grid.max_gridcells`): kept out of the user's
   view: not in generated files, not in the reference; set only from Python or tests.
